\section{集合类概述}
图片(\ref{fig:collection-framework})展示了 Java 集合框架的整体结构，包括核心接口（Collection、List、Set、Map）以及主要实现类（ArrayList、LinkedList、HashSet、TreeSet、HashMap、TreeMap 等）。

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.7\textwidth]{img/img.png}
    \caption{Java 集合框架概览}
    \label{fig:collection-framework}
\end{figure}

Java 集合框架的设计目标主要有三个：\emphasis{统一不同数据结构的使用方式}、\emphasis{屏蔽底层实现差异}、\emphasis{提供丰富且可组合的遍历和操作能力}。按照存储形式，可以将集合大致分为单列集合与双列集合两类：

\begin{itemize}
    \item \textbf{单列集合}：以 \texttt{Collection} 为根接口，典型代表是 \texttt{List} 和 \texttt{Set}。
    \item \textbf{双列集合}：以 \texttt{Map} 为根接口，保存键值对映射关系。
\end{itemize}

常见实现类的定位可以概括为：

\begin{itemize}
    \item \texttt{ArrayList}：动态数组，\textbf{随机访问快}，尾部增删高效。
    \item \texttt{LinkedList}：双向链表，\textbf{频繁插入和删除}更有优势。
    \item \texttt{HashSet}：基于哈希表的去重集合，通常无序。
    \item \texttt{TreeSet}：基于红黑树的有序集合，元素自动排序。
    \item \texttt{HashMap}：基于哈希表的键值对容器，\textbf{查询效率高}。
    \item \texttt{TreeMap}：基于红黑树的有序键值对容器，\textbf{适合范围查询}。
\end{itemize}

\note{%
List 与 Set 的区别：
\begin{itemize}
    \item \textbf{有序性}：List 保证按插入顺序排序，Set 存储和取出顺序不一致。
    \item \textbf{唯一性}：List 元素可以重复，Set 元素唯一。
    \item \textbf{获取元素}：List 可以通过索引直接操作元素，Set 不可以。
\end{itemize}
}

\subsection{ArrayList}
ArrayList 是最常用的 List 实现，底层基于\textbf{动态数组}。它的优势是\textbf{随机访问速度快}，适合频繁读取、偶尔修改的场景。

\begin{itemize}
    \item \textbf{优点}：按索引访问效率高，尾插性能好，内存连续，缓存友好。
    \item \textbf{缺点}：中间插入和删除可能需要移动大量元素。
    \item \textbf{适用场景}：读取远多于修改，例如结果缓存、列表展示、批量存储。
\end{itemize}

ArrayList 的扩容并不是每次只加 1，而是按比例扩容。这样做的目的是降低频繁扩容带来的\textbf{拷贝成本}。

\begin{codeblock}[Java]{ArrayListExample.java}
import java.util.ArrayList;
import java.util.List;

List<String> names = new ArrayList<>();
names.add("Alice");
names.add("Bob");
names.add(1, "Tom");

System.out.println(names.get(0));
System.out.println(names);
\end{codeblock}

\subsection{LinkedList}
LinkedList 的底层是\textbf{双向链表}。它在频繁插入、删除，尤其是头尾操作时更有优势。

\begin{itemize}
    \item \textbf{优点}：中间插入和删除时，不需要像数组那样整体移动大量元素。
    \item \textbf{缺点}：随机访问慢，需要从头或尾逐步查找。
    \item \textbf{适用场景}：频繁在头部、中部、尾部插入和删除的场景。
\end{itemize}

LinkedList 还实现了 \texttt{Deque} 接口，因此可用于\textbf{队列}和\textbf{双端队列}。

\begin{codeblock}[Java]{LinkedListExample.java}
import java.util.LinkedList;

LinkedList<Integer> queue = new LinkedList<>();
queue.addLast(10);
queue.addLast(20);
queue.addFirst(5);

System.out.println(queue.removeFirst());
System.out.println(queue);
\end{codeblock}

\subsection{Vector 与 Stack}
Vector 是较早的动态数组实现，方法大多带同步控制，因此\textbf{线程安全}，但性能通常不如 ArrayList。Stack 则是基于 Vector 的栈实现，遵循\textbf{后进先出（LIFO）}原则。

现在更推荐直接使用 \texttt{ArrayDeque} 作为栈结构的替代，因为它更轻量、效率更高。

\section{Set 接口与实现}
Set 表示\textbf{不允许重复元素}的集合。它没有索引概念，因此不能像 List 那样通过位置直接获取元素。对于是否"重复"的判断，核心依赖元素的 \texttt{equals()} 和 \texttt{hashCode()} 方法。

\subsection{HashSet}
HashSet 基于\textbf{哈希表}实现，元素的存放位置由哈希值决定，因此通常不保证顺序。

\begin{itemize}
    \item \textbf{优点}：查找、插入、删除通常接近 \texttt{O(1)}。
    \item \textbf{缺点}：无序，且对哈希函数质量比较敏感。
    \item \textbf{适用场景}：去重、成员判断、元素唯一性维护。
\end{itemize}

\subsection{LinkedHashSet}
LinkedHashSet 在 HashSet 的基础上维护了元素的插入顺序。它适合需要去重，同时又希望保留插入顺序的场景。

\subsection{TreeSet}
TreeSet 基于\textbf{红黑树}实现，能够对元素自动排序。默认按照自然顺序排列，也可以通过比较器自定义顺序。

\note{%
HashSet 与 TreeSet 的相同点：
\begin{itemize}
    \item 它们都不允许存储重复元素，如果传入重复元素只会记录第一个。
    \item 它们都无法通过索引去获取或修改元素。
\end{itemize}

不同点：
\begin{itemize}
    \item 底层数据结构不同，分别是哈希表和树。
    \item TreeSet 有序排列，HashSet 不一定有序。
    \item HashSet 查找效率更高（$O(1)$），TreeSet 需要比较（$O(\log n)$）。
\end{itemize}
}

\subsection{HashMap}
HashMap 是最常用的 Map 实现。它基于\textbf{哈希表}，允许 \texttt{null} 键和 \texttt{null} 值，且通常不保证顺序。

HashMap 的核心特性可以概括为：

\begin{itemize}
    \item 通过哈希函数定位桶位置，平均查询效率较高。
    \item JDK 8 之后，在链表过长时可能\textbf{树化为红黑树}，以提升极端情况下的性能。
    \item \textbf{不是线程安全的}，多线程并发修改时应优先使用 \texttt{ConcurrentHashMap}。
\end{itemize}

HashMap 的底层结构可以理解为"数组 + 链表 + 红黑树"。当多个键发生哈希冲突时，它们会落到同一个桶里；如果冲突过多，链表可能转为红黑树，以避免退化成线性查找。

\begin{codeblock}[Java]{HashMapExample.java}
import java.util.HashMap;
import java.util.Map;

Map<String, Integer> scores = new HashMap<>();
scores.put("Java", 95);
scores.put("Python", 92);
scores.put(null, 100);

System.out.println(scores.get("Java"));
\end{codeblock}

HashMap 需要特别关注两个点：

\begin{itemize}
    \item \texttt{equals()} 与 \texttt{hashCode()} 必须保持一致性，否则可能出现"放得进去、取不出来"的问题。
    \item 如果作为键的对象是自定义类，通常需要正确重写这两个方法。
\end{itemize}

\subsubsection{HashMap 底层数据结构详解}
HashMap 的底层是\textbf{数组 + 链表 + 红黑树}的复合结构：

\begin{itemize}
    \item \textbf{数组（桶）}：\texttt{Node<K,V>[] table}，是 HashMap 的主体，每个数组元素称为一个"桶"（bucket），用于存储键值对。
    \item \textbf{链表}：当多个键的哈希值相同，导致它们被映射到同一个桶时，这些键值对会以链表的形式存储在该桶中。
    \item \textbf{红黑树}：当某个桶中的链表长度过长时，为了避免 $O(n)$ 的线性查找性能瓶颈，链表会转化为红黑树，将查找时间复杂度优化到 $O(\log n)$。
\end{itemize}

\subsubsection{HashMap 关键参数}

\begin{tblr}{
  colspec = {|X[l]|c|c|X[l]|},
    row{1} = {font=\normalfont},

参数 & 默认值 & 含义 & 说明 \\
\texttt{initialCapacity} & 16 & 初始容量 & 数组的初始长度，必须是 2 的幂次方 \\
\texttt{loadFactor} & 0.75 & 负载因子 & 衡量 HashMap 填充程度的阈值 \\

\end{tblr}

\note{%
负载因子 0.75 是时间和空间成本的平衡。负载因子过高会减少空间开销，但增加哈希碰撞的概率；过低则会浪费空间。
}

\subsubsection{树化条件}
只有同时满足以下两个条件，HashMap 才会将某个桶中的链表转化为红黑树：

\begin{enumerate}
    \item \textbf{链表长度 $\geq 8$}：该桶中的链表节点数达到了 \texttt{TREEIFY\_THRESHOLD}（默认 8）。
    \item \textbf{数组容量 $\geq 64$}：整个 HashMap 的数组长度达到了 \texttt{MIN\_TREEIFY\_CAPACITY}（默认 64）。
\end{enumerate}

如果只满足第一个条件，但数组容量不足 64，HashMap 会优先选择扩容（resize），而不是树化。当红黑树节点数减少到 \texttt{UNTREEIFY\_THRESHOLD}（默认 6）时，为了节省空间和维护成本，红黑树会退化为普通链表。

\info{%
\textbf{为什么选择红黑树而不是其他平衡二叉树？}
\begin{itemize}
    \item 红黑树是\textbf{近似平衡}的二叉查找树，插入和删除操作的旋转次数较少，性能更优。
    \item 红黑树的查找、插入、删除时间复杂度都是 $O(\log n)$，且常数因子较小。
    \item 相比 AVL 树（严格平衡），红黑树对插入和删除更友好，适合频繁修改的场景。
\end{itemize}
}

\subsubsection{Hash 函数}
为了将键均匀地分布到数组的各个桶中，HashMap 使用了精心设计的哈希函数：

\begin{codeblock}[Java]{hash方法}
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
\end{codeblock}

其工作原理如下：
\begin{enumerate}
    \item 首先获取 \texttt{key.hashCode()} 的值。
    \item 然后将哈希值的高 16 位与低 16 位进行异或（\texttt{\^{}}），这一步称为"扰动"，目的是让哈希值的高位也参与到后续的下标计算中，减少哈希碰撞的概率。
    \item 最后通过 \texttt{(n - 1) \& hash} 计算出数组下标（n 是数组容量，必须是 2 的幂）。
\end{enumerate}

\subsubsection{put() 方法执行流程}
当调用 \texttt{put(key, value)} 方法时，HashMap 会执行以下步骤：

\begin{enumerate}
    \item \textbf{计算哈希值}：调用 \texttt{hash(key)} 方法计算出键的哈希值。
    \item \textbf{定位桶}：通过 \texttt{(n - 1) \& hash} 计算出应该存储在数组中的哪个桶（下标）。
    \item \textbf{处理冲突}：
    \begin{itemize}
        \item 如果该桶为空，直接将新的节点放入该位置。
        \item 如果该桶不为空，说明发生了哈希碰撞，需要遍历链表：
        \begin{itemize}
            \item 如果找到一个节点的键与 \texttt{key} 相等（通过 \texttt{equals()} 方法比较），则更新该节点的值并返回旧值。
            \item 如果遍历到链表末尾仍未找到相等的键，则将新节点添加到链表末尾（\textbf{尾插法}，JDK 8 以前使用头插法）。
        \end{itemize}
    \end{itemize}
    \item \textbf{检查链表长度}：如果添加新节点后链表长度达到 \texttt{TREEIFY\_THRESHOLD}（默认 8），则尝试将链表转化为红黑树（前提是数组容量达到 \texttt{MIN\_TREEIFY\_CAPACITY}，否则优先扩容）。
\end{enumerate}

\subsubsection{get() 方法执行流程}
当调用 \texttt{get(key)} 方法时，HashMap 会执行以下步骤：

\begin{enumerate}
    \item \textbf{计算哈希值}：调用 \texttt{hash(key)} 方法计算出键的哈希值。
    \item \textbf{定位桶}：通过 \texttt{(n - 1) \& hash} 计算出应该查找的桶（下标）。
    \item \textbf{查找元素}：
    \begin{itemize}
        \item 如果该桶为空，直接返回 null。
        \item 如果该桶不为空，说明可能存在哈希碰撞，需要遍历链表：
        \begin{itemize}
            \item 如果找到一个节点的键与 \texttt{key} 相等（通过 \texttt{equals()} 方法比较），则返回该节点的值。
            \item 如果遍历到链表末尾仍未找到相等的键，则返回 null。
        \end{itemize}
    \end{itemize}
\end{enumerate}

\subsubsection{扩容机制}
\begin{itemize}
    \item \textbf{触发条件}：当 \texttt{size > capacity * loadFactor} 时触发。
    \item \textbf{扩容过程}：创建一个新的数组，容量是原数组的 2 倍，然后将原数组中的所有节点重新哈希到新数组中。
    \item \textbf{优化}：JDK 8 中，扩容时会根据节点的哈希值与旧容量的按位与结果，将节点分为两部分，分别放到新数组的原下标和原下标 + 旧容量的位置，避免了重新计算哈希，提升了效率。
\end{itemize}

\info{%
\textbf{为什么 HashMap 的容量必须是 2 的幂次方？}
\begin{itemize}
    \item 为了使用位运算 \texttt{(n - 1) \& hash} 代替 \texttt{hash \% n}，提高计算效率。
    \item 当 n 为 2 的幂次方时，\texttt{n - 1} 的二进制全是 1，保证了下标计算的均匀性。
\end{itemize}
}

\subsection{LinkedHashMap}
LinkedHashMap 是 HashMap 的子类，它在哈希表的基础上维护了双向链表，因此既能快速查找，又能保留顺序。

它支持两种顺序模式：

\begin{itemize}
    \item 插入顺序：默认行为，元素按进入顺序排列。
    \item 访问顺序：每次访问元素后，元素会被移动到末尾，常用于 LRU 缓存。
\end{itemize}

LinkedHashMap 之所以能继承 HashMap，是因为 HashMap 预留了钩子方法：\texttt{afterNodeAccess}、\texttt{afterNodeInsertion}、\texttt{afterNodeRemoval}。HashMap 自己空实现，LinkedHashMap 重写它们来维护双向链表的结构，从而实现了元素的有序性。

\begin{codeblock}[Java]{LRUCacheExample.java}
import java.util.LinkedHashMap;
import java.util.Map;

Map<Integer, String> cache = new LinkedHashMap<>(4, 0.75f, true) {
    @Override
    protected boolean removeEldestEntry(Map.Entry<Integer, String> eldest) {
        return size() > 3;
    }
};

cache.put(1, "A");
cache.put(2, "B");
cache.put(3, "C");
cache.get(1);
cache.put(4, "D");
System.out.println(cache);
// 输出: {2=B, 3=C, 4=D} 键 1 被淘汰了
\end{codeblock}

关于 \textbf{LRU (Least Recently Used，最近最少使用)} 缓存淘汰算法，LinkedHashMap 提供了一个非常方便的实现方式。通过重写 \texttt{removeEldestEntry(Map.Entry<K,V> eldest)} 方法，可以在每次插入新元素时自动检查是否需要淘汰最旧的元素。

\warning{%
使用 LRU 缓存时，需要将 accessOrder 设置为 \texttt{true}，这样每次访问（get 或 put）都会将该元素移动到链表末尾。
}

\subsubsection{手动实现 LRU 缓存}
另一种实现方式是手动实现：手写一个双向链表来维护访问顺序，HashMap 来存储键值对和链表节点的映射关系。每次访问或插入元素时，将对应节点移动到链表头部，当缓存超过容量时，移除链表尾部的节点。

\subsubsection{为什么 JDK 8 改成尾插法？}
JDK 1.7 使用\textbf{头插法}，在并发扩容时会导致\textbf{循环链表}，从而引发死循环。JDK 1.8 改成\textbf{尾插法}，避免了环形链表的产生，但 HashMap 本身仍然是\textbf{非线程安全}的。

\warning{%
\textbf{HashMap 多线程并发问题}：
\begin{itemize}
    \item JDK 1.7 并发扩容时，使用头插法可能导致\textbf{死循环}（环形链表）。
    \item JDK 1.8 虽然解决了死循环问题，但仍然存在\textbf{数据丢失}的风险。
    \item 多线程环境下应使用 \texttt{ConcurrentHashMap}。
\end{itemize}
}

    \item JDK 1.8 解决了死循环问题，但仍不是线程安全的。

\end{enumerate}
}

\subsection{HashMap 扩容机制详解}

HashMap 的扩容过程是一个\textbf{ rehashing }的过程：

\begin{enumerate}
    \item \textbf{触发条件}：当 \texttt{size > capacity * loadFactor} 时触发（默认：size > 16 * 0.75 = 12）。
    \item \textbf{扩容过程}：
    \begin{itemize}
        \item 创建新数组，容量为原来的 2 倍。
        \item 将所有元素重新计算位置并迁移到新数组。
    \end{itemize}
    \item \textbf{JDK 1.8 优化}：扩容时不再重新计算哈希，而是利用 \texttt{(e.hash \& oldCap) == 0} 来判断元素去向。
\end{enumerate}

\note{%
扩容是\textbf{昂贵的操作}，涉及内存分配和元素迁移。如果预知数据量，应使用\textbf{带初始容量}的构造函数，避免多次扩容：
\texttt{new HashMap<>(initialCapacity)} 或 \texttt{new HashMap<>(expectedSize, 0.75f)}。
}

\section{ConcurrentHashMap 原理（面试重点）}

\subsection{为什么 HashMap 不是线程安全的？}
\begin{itemize}
    \item \textbf{数据覆盖}：多线程并发 put 时，可能导致数据覆盖。
    \item \textbf{死循环}（JDK 1.7）：并发扩容时形成环形链表，导致 get() 死循环。
    \item \textbf{putIfAbsent 问题}：复合操作不是原子性的。
\end{itemize}

\subsection{ConcurrentHashMap 的分段锁（ JDK 1.7）}
JDK 1.7 的 ConcurrentHashMap 使用\textbf{Segment 分段锁}技术：
\begin{itemize}
    \item 内部包含一个 \texttt{Segment} 数组，每个 Segment 持有一把锁。
    \item 不同 Segment 之间的操作可以\textbf{并行进行}。
    \item 锁的粒度是 Segment，而非整个 HashMap。
\end{itemize}

\subsection{ConcurrentHashMap 的 CAS + Synchronized（ JDK 1.8）}
JDK 1.8 之后，ConcurrentHashMap 放弃了分段锁，转而使用：
\begin{itemize}
    \item \textbf{CAS（Compare-And-Swap）}：用于\textbf{无锁}的读操作和部分写操作。
    \item \textbf{synchronized}：用于\textbf{加锁}的写操作，锁的粒度细化到单个桶。
\end{itemize}

这种方式比分段锁更高效，因为：
\begin{itemize}
    \item 读操作大多使用 CAS，不需要加锁。
    \item 写操作只锁定当前桶，其他桶仍可并发访问。
    \item 锁的粒度更细，并发度更高。
\end{itemize}

  colspec = {|X[l]|X[l]|X[l]|},

特性 & JDK 1.7 & JDK 1.8 \\

\begin{codeblock}[Java]{LRUCacheManual.java}
public class LRUCache<K, V> {
    private final int capacity;
    private final Map<K, Node<K, V>> map;
    private final DoubleLinkedList<K, V> list;

    public LRUCache(int capacity) {
        this.capacity = capacity;
        this.map = new HashMap<>();
        this.list = new DoubleLinkedList<>();
    }

    public V get(K key) {
        if (!map.containsKey(key)) return null;
        Node<K, V> node = map.get(key);
        list.moveToHead(node);
        return node.value;
    }

    public void put(K key, V value) {
        if (map.containsKey(key)) {
            Node<K, V> node = map.get(key);
            node.value = value;
            list.moveToHead(node);
        } else {
            if (map.size() >= capacity) {
                Node<K, V> tail = list.removeTail();
                map.remove(tail.key);
            }
            Node<K, V> newNode = new Node<>(key, value);
            list.addToHead(newNode);
            map.put(key, newNode);
        }
    }
}
\end{codeblock}

\subsection{TreeMap}
TreeMap 基于\textbf{红黑树}实现，键会按照自然顺序或比较器顺序排列。它适合范围查询、排序输出等有序场景。

TreeMap 的注意事项：

\begin{itemize}
    \item \textbf{键不能为空}，因为需要参与比较。
    \item 查询效率通常为 \texttt{O(log n)}，低于 HashMap 的平均 \texttt{O(1)}。
    \item 当需要"按顺序"访问键时，TreeMap 很合适。
\end{itemize}

\subsection{Hashtable、WeakHashMap 与 IdentityHashMap}
Hashtable 是较早的线程安全 Map 实现，整体风格偏旧，现代代码中通常更推荐 \texttt{ConcurrentHashMap}。

WeakHashMap 的键使用\textbf{弱引用}，当外部没有强引用指向这些键时，键值对可能被垃圾回收，适合做缓存或附属数据结构。

IdentityHashMap 的键比较不是依赖 \texttt{equals()}，而是依赖\textbf{引用相等（\texttt{==}）}。这使得它适用于需要"对象身份"而不是"对象内容"判断的场景。

\subsection{快速失败机制（fail-fast）}
大多数 \texttt{java.util} 普通集合迭代器（如 \texttt{ArrayList}、\texttt{HashMap}）采用\textbf{快速失败}机制。

原理如下：

\begin{enumerate}
    \item 每个集合内部维护一个 \texttt{modCount}（修改计数），记录集合结构被修改的次数（如 \texttt{add()}、\texttt{remove()}）。
    \item 每个迭代器创建时会记录当前的 \texttt{modCount} 作为 \texttt{expectedModCount}。
    \item 每次调用 \texttt{next()} 或 \texttt{remove()} 时，迭代器会检查当前集合的 \texttt{modCount} 是否与 \texttt{expectedModCount} 相等。
\end{enumerate}

如果不等，说明集合在迭代过程中被外部修改，立即抛出 \texttt{ConcurrentModificationException}，而不是继续执行不确定的逻辑。

\begin{codeblock}[Java]{FailFastExample.java}
List<Integer> list = new ArrayList<>(List.of(1, 2, 3));

for (Integer x : list) {
    if (x == 2) {
        list.remove(x); // 可能触发 ConcurrentModificationException
    }
}
\end{codeblock}

\note{%
快速失败是"尽力检测"机制，不保证 100\% 每次都在同一位置抛出。它主要用于尽早暴露并发/误用问题，不是线程安全机制。
}

为避免快速失败：
\begin{itemize}
    \item 遍历过程中，必须使用迭代器自身的 \texttt{remove()/add()} 方法修改集合。
    \item 对于并发场景，可以使用 \texttt{java.util.concurrent} 包下的线程安全集合，它们的迭代器不依赖 \texttt{modCount}，不会触发快速失败。
\end{itemize}

\caution{%
\textbf{面试重点：ConcurrentModificationException 常见场景}：
\begin{enumerate}
    \item 在 \texttt{for-each} 循环中使用集合自身的 \texttt{remove()} 方法。
    \item 多线程环境下，一个线程遍历集合，另一个线程修改集合。
    \item 单线程环境下，快速连续修改集合（如循环删除多个元素）。
\end{enumerate}
}

\subsection{fail-fast 与 fail-safe（或弱一致）对比}

\subsection{遍历与修改的安全规则}

\begin{itemize}
    \item 删除当前元素：优先使用 \texttt{Iterator.remove()}。
    \item 需要前后移动和插入修改：使用 \texttt{ListIterator}。
    \item 条件删除：优先使用 \texttt{removeIf()}。
    \item 多线程场景：优先使用并发集合，例如 \texttt{CopyOnWriteArrayList} 或 \texttt{ConcurrentHashMap}。
\end{itemize}

常用安全遍历修改方法：

\begin{codeblock}[Java]{SafeModificationExample.java}
// 方法一：使用 Iterator.remove()
List<String> list1 = new ArrayList<>(List.of("A", "B", "C"));
Iterator<String> it = list1.iterator();
while (it.hasNext()) {
    String s = it.next();
    if ("B".equals(s)) {
        it.remove(); // 安全删除
    }
}

// 方法二：使用 removeIf()
List<String> list2 = new ArrayList<>(List.of("A", "B", "C"));
list2.removeIf(s -> "B".equals(s)); // 安全删除满足条件的元素

// 方法三：倒序遍历
List<String> list3 = new ArrayList<>(List.of("A", "B", "C"));
for (int i = list3.size() - 1; i >= 0; i--) {
    if ("B".equals(list3.get(i))) {
        list3.remove(i); // 安全删除
    }
}
\end{codeblock}

\begin{codeblock}[Java]{MapTraversalExample.java}
import java.util.HashMap;
import java.util.Map;

Map<String, Integer> map = new HashMap<>();
map.put("A", 1);
map.put("B", 2);

for (Map.Entry<String, Integer> entry : map.entrySet()) {
    if ("B".equals(entry.getKey())) {
        entry.setValue(20); // 安全修改值
    }
}
\end{codeblock}

\section{深拷贝}
Java 中对象拷贝通常分为\textbf{浅拷贝}和\textbf{深拷贝}。浅拷贝只复制对象引用，深拷贝则会把对象及其内部引用对象都复制一份。

\begin{itemize}
    \item \textbf{浅拷贝}：外层对象变了，内层引用仍然共享。
    \item \textbf{深拷贝}：外层和内层对象都独立，互不影响。
\end{itemize}

深拷贝的常用实现方式包括：\emphasis{构造函数复制}、\emphasis{重写 clone()}、\emphasis{序列化复制}、\emphasis{JSON 反序列化复制}等。

        copyUser.getAddress().getCity());

\subsection{方法二：重写 clone() 方法}
\texttt{Object} 父类有个 \texttt{clone()} 的拷贝方法，不过它是 protected 类型的，我们需要重写它并修改为 public 类型。除此之外，子类还需要实现 \texttt{Cloneable} 接口来告诉 JVM 这个类是可以拷贝的。

\note{%
\texttt{super.clone()} 其实是浅拷贝，所以在重写类的 \texttt{clone()} 方法时，所有引用类型的成员变量都需要调用其 \texttt{clone()} 方法重新赋值。
}

\begin{codeblock}[Java]{CloneableClasses.java}
// 地址类，实现 Cloneable 接口
public class Address implements Cloneable {
    private String city;
    private String country;

    @Override
    public Address clone() throws CloneNotSupportedException {
        return (Address) super.clone();
    }
}

// 用户类，实现 Cloneable 接口
public class User implements Cloneable {
    private String name;
    private Address address;

    @Override
    public User clone() throws CloneNotSupportedException {
        User user = (User) super.clone();
        user.setAddress(this.address.clone()); // 关键：深拷贝
        return user;
    }
}
\end{codeblock}

\subsection{如何正确重写 equals 与 hashCode}
当对象会被放入 HashSet、HashMap 之类依赖哈希结构的集合时，\texttt{equals()} 与 \texttt{hashCode()} 必须一起重写。一般原则是：如果两个对象通过 \texttt{equals()} 判定相等，那么它们的 \texttt{hashCode()} 也必须相等。

\definition{equals()}{判断两个对象是否相等，默认实现是比较引用地址。}
\definition{hashCode()}{返回对象的哈希值，用于哈希表快速定位。}

正确重写 equals() 需要遵循以下五个原则：
\begin{enumerate}
    \item \textbf{自反性}：\texttt{x.equals(x)} 必须返回 \texttt{true}。
    \item \textbf{对称性}：\texttt{x.equals(y)} 和 \texttt{y.equals(x)} 结果必须一致。
    \item \textbf{传递性}：若 \texttt{x.equals(y)} 和 \texttt{y.equals(z)} 都为 \texttt{true}，则 \texttt{x.equals(z)} 必须为 \texttt{true}。
    \item \textbf{一致性}：在对象未被修改的情况下，多次调用 \texttt{equals()} 结果必须一致。
    \item \textbf{非空性}：\texttt{x.equals(null)} 必须返回 \texttt{false}。
\end{enumerate}

equals() 与 hashCode() 的契约关系：
\begin{itemize}
    \item 如果两个对象相等（\texttt{equals()} 返回 \texttt{true}），则它们的 \texttt{hashCode()} 必须相等。
    \item 如果两个对象的 \texttt{hashCode()} 相等，它们不一定相等（可能发生哈希碰撞）。
\end{itemize}

\note{%
如果重写了 \texttt{equals()} 但不重写 \texttt{hashCode()}，会导致"放得进去、取不出来"的问题。例如，将对象放入 HashSet 后，\texttt{contains()} 可能返回 \texttt{false}。
}

常见的问题是使用 \texttt{equals()} 判断相等但用 \texttt{==} 判断哈希相等，或反之。正确做法是始终同时重写这两个方法。

\warning{%
对于 String、Integer 等 JDK 类，它们的 \texttt{equals()} 和 \texttt{hashCode()} 已经正确实现，不需要再重写。
}

\begin{codeblock}[Java]{PersonClass.java}
// 示例：正确重写 equals() 和 hashCode()
public class Person {
    private String name;
    private int age;

    public Person(String name, int age) {
        this.name = name;
        this.age = age;
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;           // 自反性
        if (o == null || getClass() != o.getClass()) return false;
        Person person = (Person) o;
        return age == person.age &&
               Objects.equals(name, person.name);
    }

    @Override
    public int hashCode() {
        return Objects.hash(name, age);      // 使用 Objects.hash()
    }
}
\end{codeblock}

在 IDE（如 IntelliJ IDEA）中，可以使用快捷键自动生成 \texttt{equals()} 和 \texttt{hashCode()} 方法，确保正确性。

现代 Java（15+）可以使用 \texttt{record} 类型自动获得正确实现：

\end{codeblock}

\note{%
ArrayList 和 LinkedList 的时间复杂度差异主要体现在：
\begin{itemize}
    \item ArrayList 按索引访问是 $O(1)$，但中间插入/删除需要移动元素，最坏情况是 $O(n)$。
    \item LinkedList 插入/删除本身是 $O(1)$，但需要先定位到目标位置，最坏是 $O(n)$。
\end{itemize}
}

\section{总结}
Java 集合框架是一套设计精良的 API，其核心价值在于：

\begin{enumerate}
    \item \textbf{统一接口}：通过接口抽象，让不同数据结构的集合拥有统一的操作方式。
    \item \textbf{封装实现}：使用者无需关心底层是数组、链表还是树，只需要选择合适的集合类型。
    \item \textbf{丰富工具}：Collections、Arrays 工具类以及 Stream API 提供了强大的操作能力。
    \item \textbf{并发支持}：java.util.concurrent 包提供了丰富的线程安全集合。
\end{enumerate}

掌握集合框架的关键是理解：
\begin{itemize}
    \item 每个集合的底层数据结构
    \item 时间空间复杂度特性
    \item 是否有序、是否允许重复、是否线程安全
    \item 适用场景与选择依据
\end{itemize}
